**Stack evidence.** Dumps 4, 5 and 6 (about 21:11, 21:16 and 21:21) show the same stack:

`llm/client.py:962 _call_once` ← `client.py:1053 chat_with_tools` ← `curation/pathway_curator.py:316 run_pathway_curator` ← `service/postpipeline.py:1370` ← `app/streamlit_app.py:3501`

The innermost frames are an SSL socket read in the openai SDK / httpx. All 7 dumps show the script thread blocked on network I/O. No dump shows a CPU loop or a lock wait.

**Verdict.** Not a hang. The post-audit silence in E2E-1 was the curator's LLM tool loop. Its worst case is large:

- up to `max_tool_rounds=20` (`pathway_curator.py:~322`)
- each request capped at 300 s (`llm/client.py:34`; `LLM_REQUEST_TIMEOUT_SECONDS` is not set in `.env`)
- each round retried up to `LLM_MAX_RETRIES=8` times on timeout (`client.py:1035-1040`)

LLM latency varies between runs. In E2E-1 the time Stage 2 took alone was more than four times that of this run. So the 3600 s deadline in E2E-1 was a matter of time budget, not a deterministic stall. LLM calls and tokens are not logged anywhere, so the count of curator calls is unknown.

**Implication for E2E-1.** Under the shipped W4 settings (3600 s per attempt, a timeout is retryable, 7200 s wall cap), E2E-1's retry would have had a full second hour. It most likely would have passed. E2E-1 failed only because the orchestrator's outer wrapper bound was also 3600 s.

## Open questions (for the product owner)

1. **Worker time budget** (carried from `E2E-1.md`). History over 280 legs: median 18 min, p90 43 min, 15 legs over 60 min, max 93 min. This paper took 35 min (E2E-2), and more than 60 min (E2E-1).

   | option | per attempt | timeout retried? | max time the one worker is held | cost |
   |---|---|---|---|---|
   | (a) keep as shipped | 60 min | yes | 2 h | a slow paper costs 2 runs of LLM spend and holds the queue up to 2 h; E2E-1 would likely have passed on retry |
   | (b) one long attempt | 90 min | no | 90 min | covers all but about 1 of 280 historical legs; no double spend; a stall that is not LLM latency fails after 90 min |
   | (c) long attempt + retry | 90 min | yes | 3 h | the most completions; the worst queue hold |

   **Recommended: (b).** The timeouts seen are LLM-latency variance inside one run, and a longer single attempt absorbs that more cheaply than a full restart. This is a web-layer change only (`web/retry.py`), with no biology.
2. **The curator's LLM budget is effectively unbounded** (20 tool rounds × 300 s × up to 9 tries). Capping it is a change under `curation/`, which is outside the web track. It is recorded here for a biology-side task if the PO wants one.
3. **Observability.** The server cannot report LLM calls, tokens or the time spent per stage. That is needed for the paper's performance section and for the server's status page. Where to log it (worker side or `llm/client.py`) is a scoping decision.
