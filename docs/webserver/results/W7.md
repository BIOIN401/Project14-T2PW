### Worker hook: two call sites, not one

The brief asked for a single call. An item becomes final in two places: `Worker._finish`
(every run outcome, including the containment-error path) and `Worker.start()` (items the
previous worker died on, finished by `recover_running`). One call in `_finish` alone would
never notify for a crash recovered at restart. Both sites call the same `postrun.run`,
which returns at once for an item that is not `finished` (a re-queue). No other worker
logic moved.

## Qualification rule

All must hold (`curator_queue.qualify`); the first four are the PO ruling
(`PO-RULINGS-2026-11-04.md`, Q-W0-3/5):

1. `item.state == finished` (final; a re-queued item is `queued`, `jobs.py` `finish(requeue=True)`).
2. submission `consent` is on (stored by W3).
3. `item.request.export_mode == "strict"` (`MODE_STRICT`, `service/pathway.py:29`).
4. `result.release_status.status == "release_ready"` (`RELEASE_READY`,
   `pipeline/release_status.py:47`; `ReleaseStatus.status` is the field at `:455`). A
   `review_required` or `diagnostic_only` status never qualifies. The filename of the PWML is
   not consulted (W0 design choice 4).
5. `result.pwml_path` names an existing file under the worker's work root.

The work-root check is mine: the result dict comes from a child process, so a path in it is
not followed unless it is inside the directory the worker gave that run. The same check
applies to every report.

## Files copied, and why

Layout of `entry-<item_id>/`: `pathway.pwml`, `provenance/<key>`, `citations/<key>`,
`manifest.json`. Provenance = the `report_paths` keys (names from the W0.md group table /
`driver.py` `RunOutcome.artifacts`) that tell a curator where each element came from and
what the strict run did to it:

| key | why |
|---|---|
| `merged_payload.json` | the evidence-bearing extraction the PWML is built from |
| `final_mapped.json` | entity identity / database ids of every element |
| `rag_admission_report.json` | which RAG-sourced facts were admitted, and why |
| `contract_reports.json` | stage-boundary contract results |
| `final_stage3_gate_report.json` | the biological gate verdict that released it |
| `quarantine_report.json` | what the strict run quarantined |
| `removed_entity_report.json` | what it removed (a curator must see omissions) |
| `coverage_summary.json` | completeness against the requested pathway |
| `pwml_validation_report.json` | the exported PWML was validated |
| `pwml_required_field_gate_report.json` | required PathBank fields present |

Not copied: diagnostics (`stage0_attempts`, `cleaning_report`, ...), `stage1_payload` and
`initial_stage3_gate_report` (earlier drafts of what `merged_payload` / `final_...` supersede),
`gate_fail_report` (failure-only), scope files, `coverage_diagnostics`,
`graph_closure_iterations`, `pwml_ir*` (intermediate). Citation: `research_pathway_citations.json`
only (its `.txt` / `.csv` views are not copied). It exists only in research mode (W0 F5), so a
strict result normally has none; it is copied when present, which matches the PO ruling.
A listed provenance key the run did not write goes in the manifest's `provenance_not_available`;
it does not block the entry.

## Manifest schema (`manifest.json`, schema 1)

`schema`, `job_id` (= submission id; the job page is `/jobs/<submission id>`), `submission_id`,
`item_id`, `organism` (`scope.requested_organism`), `pathway_name` (`scope.requested_pathway`),
`export_mode`, `release_status` (the `ReleaseStatus.to_dict()` record), `consent`,
`enqueued_at` (epoch s), `files` (list of `{role: pwml|provenance|citation, path, bytes,
sha256}`), `provenance_not_available`. Table row: `item_id` (PK), `submission_id`, `organism`,
`pathway`, `entry_dir`, `status` (`pending|imported|rejected`), `note`, `created_at`,
`decided_at`.

## Idempotency and atomicity

`item_id` is the table's primary key and the folder name is `entry-<item_id>`. An existing
row returns as is. The entry is built under `.tmp-entry-<id>-<uuid>` (each file written to
`name.tmp`, fsynced, `os.replace`d; manifest last), then `os.rename`d into place; the row is
inserted last (`INSERT OR IGNORE`). A crash after the rename and before the insert leaves an
orphan folder; the next enqueue sees the folder, skips staging and inserts the row (tested).
On an exception the code removes only its own `.tmp-*` folder. The module has no PathBank
or external-DB code.

## Exactly-once email

`web_notifications(submission_id PK, outcome, state sending|sent|not_sent)`. When the last
item of a submission is final, `_claim` does `INSERT OR IGNORE`; only the call whose insert
took effect calls `notify_job`, then records `sent` / `not_sent`. Later items, a repeat call
and a restarted worker find the row and send nothing. Outcome: `finished` if any item has
`status == pass`, else `failed`. Link: `<base_url>/jobs/<submission id>`, `base_url` passed
to `notify_job` (W8 F4). No email address on the submission, or no `T2PW_BASE_URL`: no call
and no row.

Cost of this design: **at-most-once**. A crash between claim and send loses the email (row
stays `sending`); a failed send (SMTP down) is recorded `not_sent` and not retried.

All failures in `run` are caught and logged as the exception class and an id only (no
address, no message text, no secret); the item's persisted result is never written by this
code.

## Dead ends and things not done

- **A sweep at start-up** that emails every all-final submission without a claim row was
  considered and dropped: on the first deploy against an existing DB it would email every
  historic submission. The remaining gap is a crash between `store.finish` and the hook
  (a few ms); the curator enqueue is idempotent but nothing re-triggers it. See Q-W7-3.
- **Retrying a failed send** (a `not_sent` row) was dropped: it gives at-least-once and risks
  duplicates, which the brief ruled out.
- **Copying the PWML under its source name** (`pathway.pwml` vs `.review_required.pwml`)
  was dropped: the entry always holds `pathway.pwml`, and the manifest `release_status` says
  what it is.
- No `shutil.copy2`: it is not atomic. A hand-rolled short copy gives the temp-file + replace
  and the sha256 in one pass.

## Open questions

**Q-W7-1. Provenance list.** Is the 10-key list right, and should a release_ready entry with
*no* provenance file at all still be queued? Now: queued, the gap listed in the manifest.

| option | cost |
|---|---|
| A (now) | queue it, flag the gap. No consented pathway is silently dropped; a curator may get a bare PWML |
| B | refuse to queue it. Curator sees only fully documented pathways; a consented one never reaches the queue and nothing says so |

**Q-W7-2. Failure emails.** Both outcomes send (`finished` / `failed`), which is W8's Q-W8-3.
If the PO wants success-only, it is one condition in `postrun.run`.

**Q-W7-3. At-most-once email.** Options: (A, now) at-most-once, lost on a crash in the claim-send
window; (B) add a `sending` timeout so a stuck claim is retried: at-least-once, small duplicate risk;
(C) start-up sweep of un-claimed all-final submissions: fixes the finish-to-hook gap but emails
history on first deploy unless it is limited to submissions newer than a cut-off.

**Q-W7-4. Retention.** Queue entries (and the copies) are kept forever; imported / rejected entries
are not pruned, and the work-root copies of the same files are governed by W3/W8 retention.

**Q-W7-5. Curator surface.** Only the Python read API exists; a CLI or page is for a later task
(W6 owns templates). Nothing authenticates a curator: whoever can reach the DB can mark entries.

### N3: operational notes (for W9)

- `notify_job` runs synchronously inside the worker, so a slow or hung SMTP server stalls
  the queue for up to `notify.SMTP_TIMEOUT_S` (10 s) per submission.
- An unconfigured SMTP (no host or from-address) makes `notify_job` return False, and the
  claim row is then recorded `not_sent` for good; the email is never retried. SMTP and
  `T2PW_BASE_URL` must be configured before real jobs run.
- The email gap that the sweep does not cover: a crash between `store.finish` and the hook
  still loses that submission's email (Q-W7-3, option A unchanged). The sweep fixes the
  curator enqueue only.
