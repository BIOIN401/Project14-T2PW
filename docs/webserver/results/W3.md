### Store (`jobs.py`)

There are three tables:

- `submissions(id, created_at, consent DEFAULT 1, email)`
- `items(id, submission_id, position, request_json, state, attempt, deadline, status, failure_kind, result_json, created_at, started_at, finished_at)`
- `attempts(item_id, attempt, started_at, deadline, finished_at, child_pid, exit_code, status, failure_kind, message)`

How it behaves:

- **`submit(requests, consent=True, email=None)`** takes 1 to 5 `PathwayRequest`s.
  - 0 or 6 items raise `ValueError`. A non-request item raises `TypeError`.
  - It raises `QueueFull` if the queued plus running items would exceed `MAX_QUEUED_ITEMS`.
  - It is all or nothing. The cap check and the insert run in one `BEGIN IMMEDIATE`
    transaction, so two web processes cannot both slip under the cap.
  - Consent and email are stored only. W7 and W8 act on them.
- **Item states** go `queued` → `running` → `finished`.
  - `finished` means only that the item is no longer being worked on. How it ended is in
    `status` and `failure_kind`, which use the W0 vocabulary (`pass`, `timeout`, `error`,
    and so on).
  - W4 can re-queue an item by setting `state='queued'`. The next claim bumps `attempt`
    and opens a new `attempts` row, so W4 needs **no schema change**. W3 never retries.
- **`claim_next(timeout_s)`** takes items oldest first, by item id. It sets
  `deadline = now + timeout_s` **at dequeue**, along with `attempt + 1`, `started_at` and
  a new attempts row.
- **`finish(item_id, attempt, result, exit_code)`** persists the result dict in
  `result_json` and copies `status` and `failure_kind` into their own columns.
  - It is guarded by `attempt` and `state='running'`, so a stale write returns `False`
    and changes nothing.
  - `result_to_dict` copies every `PathwayResult` field. `release_status` goes through
    `ReleaseStatus.to_dict()`, and paths become strings.
- **`recover_running()`** finishes every `running` item as `status=error`,
  `failure_kind=crash`, `stage=init`, with the message "the worker stopped while this
  item was running (attempt N); ...". It closes the matching attempts row. It does not
  re-queue anything (see Q-W3-2).
- The database runs in WAL mode with `timeout=30` and foreign keys on.

### Worker (`worker.py`)

1. **`start()`** takes an exclusive, non-blocking lock on `<work_root>/worker.lock`
   (`msvcrt.locking` or `fcntl.flock`). The OS releases the lock if the process dies. A
   second worker on the same work root raises `RuntimeError`. Only after taking the lock
   does `start()` run `recover_running()`. That order makes recovery deterministic: an
   item is `running` at start-up only if its worker is dead.
2. **`run_one()`** claims an item and builds `replace(request, deadline=<dequeue
   deadline>, out_dir=request.out_dir or <work_root>/item-<id>/attempt-<n>/out)`. It then
   starts `sys.executable -m t2pw.web.worker --child <run_fn> <result.json>`. The child's
   stdout and stderr go to `child.log` in the same attempt directory.
3. **Containment.**
   - On Windows, the child gets `CREATE_NEW_PROCESS_GROUP`. Right after `Popen`, the
     worker assigns it to a new Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. This
     is the `bounded_run.py` pattern, reduced to the four kernel32 calls it needs.
   - On POSIX, the child gets `start_new_session=True`, so its process-group id equals its
     PID.
   - The request reaches the child on stdin, and only after containment, so the run
     cannot start before the worker owns the tree.
4. **The child** imports `run_fn`, which is `module:attr` and defaults to
   `t2pw.service.pathway:run_pathway`. It calls the function and writes
   `result_to_dict(result)` atomically (tmp file, then `os.replace`). Any exception, or a
   return value that is not a `PathwayResult`, becomes `error` / `crash` with the
   exception text in `message`.
5. **Deadline.** The worker calls `proc.wait(timeout=deadline - now)`. If the deadline
   passes, it kills the tree and records `status=timeout`, `failure_kind=timeout`,
   `stage=init`, with the message "killed at the deadline (N s after dequeue)". A child
   that exits without a readable result is recorded as `error` / `crash` with its exit
   code.
6. **Tree kill, on every exit path.** The kill runs in a `finally` block, so it also runs
   after a normal exit and catches any leftover grandchild.
   - On Windows it calls `TerminateJobObject` on the worker's own job handle. If that job
     could not be created, it falls back to `taskkill /F /T /PID <own child>`.
   - On POSIX it calls `os.killpg(<own child pid>, SIGKILL)`.
   - It never kills by image name. It goes straight to a forced kill: a pipeline killed at
     its deadline has nothing to save gracefully.
7. **Worker death.**
   - On Windows, the dead worker's Job Object handle closes, and kill-on-close takes the
     child tree with it. This is proven below.
   - On POSIX, the child starts a daemon thread that polls `os.getppid()`. When the child
     is re-parented, the thread calls `os.killpg(own group, SIGKILL)`. systemd's default
     `KillMode=control-group` also kills the unit's whole cgroup when the service stops or
     restarts. This path is **not exercised on Linux** (see Q-W3-3).
8. **Import isolation.** Neither `t2pw.web.jobs` nor `t2pw.web.worker` imports
   `streamlit` or `t2pw.app`. A test checks this in a fresh process.

## Findings

1. **A venv `python.exe` on Windows is a launcher with the real interpreter as its
   child.** Run 01 failed because `attempts.child_pid` (the launcher) was not equal to the
   run's `os.getpid()` (the real interpreter). This means "the child" is already a
   two-process tree on Windows. Killing only the recorded PID would not be enough without
   the Job Object. The test now treats both PIDs as the tree.
2. **The launcher's own job does not cover the run's descendants.** Mutation A killed
   only the launcher PID, and the grandchild survived. So the worker's own Job Object is
   what kills the tree, not the launcher. The timeout test does discriminate.
3. **Kill-on-close is what makes worker death safe on Windows.** With the flag removed
   (mutation B), a killed worker left 3 processes alive (launcher, interpreter,
   grandchild). With the flag set, it left none.
4. **Caveat on the killed-worker test.** The test kills the worker's launcher PID. The
   venv launcher takes its real interpreter down with it, so this is effectively an
   abrupt `TerminateProcess` of the whole worker. That is the crash case being modelled.
   On Linux under systemd there is no launcher layer.

## Dead ends and things not done

- **`multiprocessing` instead of `subprocess`.** I rejected it. It gives no process
  group or session on spawn, so the child tree would still need a Job Object and a
  `setsid` call inside the child. It also has to pickle the run function, and it leaves
  no way to start the run *after* containment. With `subprocess` and a request on stdin,
  all three come out of the design for free.
- **Killing an orphaned child at recovery by its stored PID.** I rejected it: after a
  restart the PID may already belong to another process. The child's tree is instead
  made to die with the worker (Job Object kill-on-close, the POSIX parent watchdog,
  systemd's cgroup).
- **A graceful stage before the kill** (as `bounded_run.py` does). Not done: nothing in
  a killed pipeline run needs a clean shutdown. This is one line to add if wanted.
- **A race on Windows (WRONG in round 0, fixed in round 1).** Round 0 claimed that
  between `Popen` and the Job Object assignment the child "cannot have spawned
  anything". **That was false.** A venv `python.exe` is a launcher, and it can start
  the real interpreter before the assignment. That interpreter is then outside our
  job, and its descendants escape `TerminateJobObject`. Mutation C (round 1) proves it.
  The `taskkill /T` fallback was uncontained as well. Both are replaced: see "Review
  round 1", F2.
- **Not done:**
  - Cleanup of attempt directories, and disk quotas (W9).
  - A `stage` for a timed-out item. The killed child cannot report one, so it is `init`.
  - Retries (W4).
  - Email and consent actions (W7, W8).
  - Exercising the POSIX branch: no Linux host in dev.

## Open questions

**Q-W3-1. The queue cap default.** `MAX_QUEUED_ITEMS = 20` open items (queued plus
running), across all users.

| option | cost |
|---|---|
| A: 20 (current) | At 20 to 60 minutes per run with one worker, the last item waits about 7 to 20 hours. Four full submissions fill it |
| B: 50 | A backlog of up to about 2 days. Users may wait longer than they are willing to |
| C: 10 | About 3 to 10 hours. Two full submissions fill it, and public users will hit "queue full" often |
| D: a per-IP cap as well (W8) | More code in W8. Stops one user filling the queue |

**Q-W3-2. The restart policy for an orphaned `running` item.** Current choice: finish it
as `error` / `crash` and do not re-run it. W4 can then retry it, since a crash is an
infrastructure failure.

| option | cost |
|---|---|
| A: mark crash; W4 decides (current) | Deterministic. A run that kills the worker (for example by running out of memory) is not retried by W3 in a loop. The user sees one crash until W4 lands |
| B: re-queue it at the same attempt | Silent and transparent to the user, but a worker-killing input loops forever, and nothing records the lost attempt |
| C: re-queue it with `attempt + 1`, capped | This is a retry policy, so it belongs in W4 |

**Q-W3-3. The Linux kill method.** Current: `start_new_session` plus `killpg(SIGKILL)` at
the deadline, plus a `getppid()` watchdog thread in the child for worker death, plus
systemd's `KillMode=control-group`. None of it has run on Linux.

| option | cost |
|---|---|
| A: current, verified on the server in W9 | No code. It needs one manual check on the host: kill the worker mid-run and confirm no survivors. The watchdog misses a grandchild that calls `setsid` itself. The cgroup catches that one |
| B: `prctl(PR_SET_PDEATHSIG, SIGKILL)` through ctypes in the child | About 5 lines, Linux only. It covers only the direct child, so the watchdog's group kill is still needed |
| C: rely on systemd only (drop the watchdog) | Less code. A worker crash that systemd does not restart, or a worker run by hand in dev, leaves the child running and billing the LLM |

**Q-W3-4. `RUN_TIMEOUT_S = 3600`** is a W3 placeholder that matches the batch leg
timeout. W4 owns the per-pathway wall-clock cap (D-W07). It can pass `timeout_s` or
change the constant.

**Q-W3-5. Order.** Items run oldest first by item id, so all of one submission runs
before the next submission. Round-robin across submissions would be fairer to a user who
submits 1 item behind someone else's 5. That is a small change to `claim_next`.

### F6 reasoning (POSIX, not executed)

The goal is that `os.killpg(pid, SIGKILL)` only ever signals our own group. A process
group's id is its leader's PID. Linux does not reuse a PID while any process still uses it
as a PID, a pgid or a sid. The leader holds its PID until it is reaped, so while it is an
unreaped zombie the number cannot go to anyone else.

1. **`_Child.wait_unreaped(deadline)`** polls
   `os.waitid(os.P_PID, pid, WEXITED | WNOHANG | WNOWAIT)` every 0.2 s until the deadline.
   - `WNOHANG` makes the call return `None` while the child runs.
   - `WNOWAIT` reports the exit but leaves the child a zombie.
   - Nothing calls `Popen.poll()` or `wait()` before the kill, so `subprocess` does not
     reap it either.
2. **`kill_tree`** then calls `killpg(pid, SIGKILL)`.
   - If the leader has exited, the group still exists: a zombie keeps its pgid. The signal
     reaches any surviving member, and is harmless to the zombie.
   - If the leader is still running (the deadline case), it and every member die.
   - `ProcessLookupError` is ignored, though by the argument above it should not happen.
3. **Only then does `self.proc.wait()` reap**, and the PID becomes reusable.

The `finally` block in `run_one` runs `kill_tree` on every exit path. An exception can only
arrive before the reap, so the same order holds. **What this cannot catch:**

- A descendant that called `setsid()` or `setpgid()` itself leaves our group. The systemd
  cgroup is the backstop for that.
- On macOS, `os.waitid` is absent in some builds. The server is Linux.
