### Flow

1. An attempt ends (result read from the child, a deadline kill, a crash, or a
   containment failure). The worker calls `decide`.
2. **RETRY:** `store.finish(..., requeue=True)` closes the attempt's `attempts` row with
   its status, kind, message and exit code, then sets the item back to `queued`. The
   item-level `status`, `failure_kind` and `result_json` are cleared, so a queued retry
   never looks like a failed outcome. It stays `queued`, so it still counts toward
   `MAX_QUEUED_ITEMS`.
3. **FINAL:** the old path. The item is `finished` with the result.
4. The next `claim_next` bumps `attempt`, opens a new `attempts` row, and sets
   `deadline = now + min(timeout_s, wall_cap_s - wall_used)` at dequeue.
   A retry keeps its item id, so it is claimed before newer items (see Q-W4-2).
5. **Restart:** `Worker.start()` calls `recover_running(self._should_retry)`. The orphaned
   `running` item is still first closed as `error` / `crash` in its attempts row (W3
   behaviour), and the same `decide` then picks retry or final. `recover_running()` with
   no argument behaves exactly as in W3.

### Decision order in `decide`

(Updated in review round 1, F1.)

1. `status == scope_conflict` -> final.
2. `release_status` is not `None` -> final, whatever the kind (the run reached a verdict).
3. `failure_kind` in `contract`, `ambiguous_review_scope`, `no_reactions` -> final.
4. `status == pass` with a `pwml_path` -> final.
5. `failure_kind` in `timeout`, `crash`, `llm`, `network` -> retry candidate.
6. `status == error`, `failure_kind` in `""`, `unknown`, no `pwml_path` -> retry candidate
   ("no PWML"; `release_status` is already known to be `None` from check 2).
7. Anything else (an unrecognised kind, a `fail` or `pass` without a PWML) -> final. Fail closed.
8. A candidate is still final if `attempt > max_retries` (the 3rd attempt), or if less
   than `MIN_RETRY_BUDGET_S` of the wall cap is left.

Checks 1 to 3 run before 4 and 5, so no infrastructure kind can override a verdict.

## Caps

All are module constants in `src/t2pw/web/retry.py`.

| constant | value | why |
|---|---|---|
| `MAX_RETRIES` | 2 | D-W07. At most 3 attempts |
| `RUN_TIMEOUT_S` | 3600 | Per attempt, from dequeue. PLAN s1: runs take about 18 to 60 min and the batch leg timeout is 60 min. It is the W3 placeholder value, now owned here (answers Q-W3-4) |
| `PER_ITEM_WALL_CAP_S` | 7200 | Run time summed over all attempts of one pathway. Queue waits are not counted. Two hours means a first attempt that times out at 60 min still leaves a full 60 min for its retry. A cap of 3 x 60 min would bound nothing that the attempt cap does not. The cap also bounds how long one pathway can hold the single worker (worst case 2 h) |
| `MIN_RETRY_BUDGET_S` | 900 | No retry starts with under 15 min of the cap left. The fastest runs take about 18 min, so a smaller budget buys a certain timeout |

So with the defaults: a first attempt that times out leaves room for exactly one more
full-length attempt (2 attempts). The 3-attempt chain happens when failures are quick,
which is the case the policy is for (empty LLM replies, a network blip).

**Delay between attempts: none.** A retry is claimed at the next `run_one`. Reasons:
the in-run LLM client already retries and backs off inside an attempt (`attempt_log`);
an attempt takes minutes before it can fail, which is already a long gap; and a delay
needs a `not_before` column and a change to the `claim_next` ordering (schema change,
beyond the brief). The cost is in Q-W4-2.

**Open-attempt accounting.** An attempt still open (a worker died) is charged up to its
own deadline at most: `MIN(now, deadline) - started_at`. The worker kills at the
deadline, so it cannot have run longer. It may have run less: the downtime of a dead
worker is then charged to the item, which is conservative (see Q-W4-3).

## Attempt-history query (for W6)

`JobStore.attempt_history(item_id)` returns one dict per attempt, oldest first:
`attempt`, `started_at`, `finished_at` (None while running), `status`, `failure_kind`,
`message`, `retried` (a later attempt exists) and `will_retry` (it failed and the item is
queued for the next attempt). A running attempt has both flags False (undecided). A final
attempt has both False. An unknown item gives `[]`. `store.item(id)["attempts"]` still
returns the raw rows as before.

   migration for an existing database and a `claim_next` ordering change. The job-level
   retry already follows an attempt of minutes and an in-run LLM backoff.
4. **Considered and rejected: a separate `retried` / `retry_reason` column.** `retried`
   and `will_retry` are derivable from `attempts` plus the item's `state` and `attempt`,
   so no migration. The reason string from `decide` is not persisted (Q-W4-4).
5. **Considered and rejected: retrying on `status == timeout` regardless of kind.** The
   worker and the driver both set `failure_kind = timeout` with it, so the kind covers it.
6. **Not done:** retrying a kind the policy does not know (fail closed); checking that

## Open questions

**Q-W4-1 (updated in round 1). Does D-W07's "no-PWML outcomes" mean only a run that broke?**
Round 0 retried any non-verdict outcome with no PWML. The reviewer showed that strict-mode
gate refusals can arrive as `fail` / `unknown` with no PWML and no `release_status`, and a
retry would re-roll the LLM until a gate passes (merge gate 6). The code now retries a
no-PWML result only when status is `error`. This is my narrowing of the D-W07 wording, an
interpretation the PO must confirm.

| option | cost |
|---|---|
| A: `error` only (current) | Safe for the gates. A transient `fail` / `unknown` with no PWML is shown as failed, and the user resubmits |
| B: also `fail` / `unknown` | Matches the wider reading of D-W07. Can re-roll a gate refusal; only acceptable if the driver gives `fail` a structured gate-refusal marker (a driver change, outside W4) |
| C: A, plus a retry of `fail` / `unknown` only when the driver reports `operational_failure` | Needs R5 to carry the driver's `operational_failure` into `PathwayResult` (service is frozen) |

**Q-W4-2. Order and delay.** A retry keeps its item id, so it runs next, before items
queued behind it, with no delay.

| option | cost |
|---|---|
| A: current | A provider outage burns attempts 1 to 3 within minutes and fails the item before the outage ends. A retried item delays everyone behind it (bounded by the 2 h cap) |
| B: a fixed delay (e.g. 5 min) via a `not_before` column | Schema migration, `claim_next` change. Gives short outages time to clear. The worker idles unless the query skips delayed items |
| C: send retries to the back of the queue | A `claim_next` ordering change (for example order by last activity). Fairer, but a user's retry waits behind a possible 20-item backlog (7 to 20 h, Q-W3-1) |

**Q-W4-3. Worker downtime counts against the wall cap.** An attempt open when a worker
dies is charged to its deadline (up to 60 min), not to the time it really ran. A deploy
that restarts the worker mid-run therefore uses up to an hour of that item's 2 h.

| option | cost |
|---|---|
| A: current | Conservative and simple. After a restart the item has at least 1 h left and gets one more attempt |
| B: a worker heartbeat column, charging up to the last beat | A column and a periodic write. Exact accounting |
| C: charge restart-crashed attempts nothing | An infinite-loop risk is then bounded only by the attempt cap (3), not the wall cap |

**Q-W4-4 (round 1, F5: no schema change). Show the reason for "not retried"?** Decided: no
column. W6 derives the reason from the last attempt's `failure_kind` (and from `attempt`
being 3 or the cap). The original question follows.

**Q-W4-4 original text.** `decide` returns a reason (for example
"final: per-pathway wall-clock cap"), but it is not stored, so the job page cannot tell
the user why a failed item was not retried. Option A: leave it, derive a message from
`failure_kind` in W6. Option B: add a `retry_reason` column (an `ALTER TABLE` guarded by
`PRAGMA table_info`, about 5 lines) and fill it in `finish`. Option B is cheap, but it is
a schema change, which the brief did not ask for.

**Q-W4-5. `PER_ITEM_WALL_CAP_S = 2 h` and `RUN_TIMEOUT_S = 1 h`.** Both are judgement
from PLAN s1 (18 to 60 min). The first real end-to-end public job (W6 to W9) is the first
evidence. If real runs mostly finish in 30 min, a 1 h attempt timeout wastes worker time on
hangs; if some legitimate runs need more than 1 h, they will time out twice.
