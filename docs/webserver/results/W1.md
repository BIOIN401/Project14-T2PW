## What was built

`src/t2pw/service/inputs.py` (273 lines). It is not wired into `run_pathway`; `pathway.py`
and `service/__init__.py` are untouched. All three adapters return plain dataclasses and
never drop an input silently.

| Mode | API | Result |
|---|---|---|
| name + organism | `name_to_spec`, `resolve_name` | `NameInputs(spec, scope, papers, skipped, stats, message)` |
| PMIDs | `validate_pmid`, `resolve_pmids` | one `PmidResult(pmid, status, pmcid, text, message)` per distinct input |
| PDFs | `read_pdfs` | one `PdfResult(path, status, text, method, warnings, message)` per path |

PMID statuses: `ok`, `invalid`, `no_pmcid`, `no_full_text`, `lookup_failed`. The last
exists so an NCBI outage is never reported as "no open-access full text" (that would tell the
user to upload a PDF they may not need). `no_pmcid` and `no_full_text` both carry exactly
`no open-access full text found for PMID X; please upload the PDF`.

PMID validation: `^[1-9]\d{0,8}$` after `strip()`. Deliberately not `batch.fetch._PMID_RE`
(6+ digits): that regex exists to tell a bare token from a topic, whereas here a short PMID
is legitimate. Invalid ids come back as `invalid` results, not exceptions.

PDF adapter checks the `%PDF-` magic before calling the parser, and reports non-PDF,
unreadable, parser-error and empty-text files each with a message.

## Dead ends and findings

1. **No idconv helper exists anywhere in the repo** (`grep -ri idconv src` finds nothing).
   `_idconv` in `inputs.py` is new: one batched GET (100 ids a call) to
   `https://pmc.ncbi.nlm.nih.gov/tools/idconv/api/v1/articles/`, built on the reused
   `HttpClient` and NCBI params.
2. `rag.acquire._resolve_europepmc_item` already turns a PMID into a PMCID through a Europe
   PMC search, so `fetch_full_text` could take a bare PMID directly. Not used: the brief asks
   for idconv, and idconv gives a distinct "no PMCID" signal before any full-text download.
   Option below.
3. idconv returns a PMCID for records that are in PMC but not in the open-access subset;
   open access is only established when Europe PMC `fullTextXML` returns text. So `no_pmcid` and
   `no_full_text` are separate statuses with the same user message.
4. Throttle is applied only when the default client is used; an injected client is the
   caller's responsibility (keeps tests instant).
5. Nothing was run live. The idconv URL and the response shape (`records[]`, `pmid`, `pmcid`,
   `status: "error"` for unknown ids) are from NCBI's documentation, not verified here. See
   Open questions.

## Open questions

1. **Live idconv check.** The endpoint and response shape were not exercised against NCBI.
   Option A: the test-runner or PO makes one live call with a known PMID before merge (cheap,
   removes the risk). Option B: ship and watch the first real job. Cost of being wrong:
   every PMID reports `lookup_failed` or `no_pmcid`, a visible but not data-losing failure.
2. **idconv vs Europe PMC for PMID -> PMCID.** Keeping idconv adds one network dependency;
   dropping it (pass the PMID straight to `fetch_full_text`) saves a call but loses the
   separate "no PMCID" signal. Kept as briefed.
3. **Disk cache in `resolve_pmids`.** The default `fetch_full_text` caches under
   `data/rag_index/acquire_cache/fulltext/` (the same cache name mode uses). Fine for a single
   server; a read-only or per-job filesystem would need a `cache_dir` passed through. W1 does not
   expose it (the file boundary stops at `inputs.py`); `fetch_text_fn` is the escape hatch.
4. **Limits.** No cap on the number of PMIDs, PDFs or PDF size here; W8 (size/page caps) and
   W3 (max 5 pathways per submission) own that. `resolve_name` defaults to `count=3`
   (`DEFAULT_PER_TOPIC`); the product may want a different number of papers per name request.
5. **R5 hand-off shape.** `PathwayRequest.texts` takes strings, `pmids` takes ids. R5 should
   decide whether it feeds `PmidResult.text` / `PdfResult.text` / `BatchPaper.full_text` into
   `texts` (so fetching happens once, here) or re-fetches from `pmids`. W1 only supplies the data.
