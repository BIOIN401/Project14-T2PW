### Design choices and why

1. **Pathway name and organism go in `scope: RequestedScope`.** `RequestedScope`
   (`rag/eligibility.py:1014`) is already frozen and already what the batch passes for the
   same two facts. PLAN R5 lists "pathway name, organism", which are
   `scope.requested_pathway` and `scope.requested_organism`. The caller sets `pinned` with
   the driver's rule (`driver.py:582-597`, `pinned = not pathway`): name mode means
   `pinned=False`, and PMID/PDF-only mode (no pathway name) means `pinned=True`. W0 does
   not re-implement that rule. W1 owns building the scope.
2. **The request is frozen.** This is the same rule `RequestedScope` enforces: the run may
   not rewrite its request. List fields are tuples, so the frozen object stays hashable.
3. **The vocabulary is mirrored, not imported, and a test pins it.** I took the brief's
   "mirror + test" option because:
   (a) R6 makes `batch/driver.py` call `run_pathway`, so the service importing the driver
   would create an import cycle;
   (b) the driver's status names are private (`_STATUS_*`);
   (c) the driver module is large and pulls the pipeline gate modules.
   `STATUS_SCOPE_CONFLICT` is imported from `OUTCOME_SCOPE_CONFLICT`, exactly as the driver
   does, so that string has one source. The test compares the full prefix sets both ways,
   so a constant added to the driver and not here fails it. `STAGE_APP_LOAD` is
   AppTest-specific and is still mirrored, to keep the equality simple.
4. **`release_status` was added beyond the PLAN R5 list.** W7 must know whether a PWML is
   strict/release-ready. The only other signal is the filename (`pathway.pwml` vs
   `pathway.review_required.pwml`, `driver.py:2041-2043`), and `RunOutcome`'s own comments
   forbid inferring release status from a filename. It uses the existing `ReleaseStatus`
   type, so nothing is redefined. If PO/orchestrator disagree, see Q-W0-3.
5. **`stage` and `message` were added beyond the PLAN list.** The brief names the stage
   vocabulary. W4/W6 need to say *where* a run failed and show a human-readable reason.
   Both fields mirror `RunOutcome`.
6. **The defaults mirror `RunOutcome`.** An unfilled `PathwayResult` reads as
   `error`/`init`, never as a pass.
7. **Consent, email and job id are not in the request.** The pipeline does not read them.
   They belong to W3/W7/W8.

### What the stub returns

For every request, it returns:

```python
PathwayResult(status="error", stage="init", failure_kind="unknown",
              message="run_pathway is a W0 stub: no pipeline ran. R5 implements it.")
```

It ignores the request, writes nothing (the test passes an `out_dir` and asserts it is not
created), and makes no network or LLM call. It is deterministic: two calls return equal
results. It is marked STUB in the module docstring, the function docstring and the message.

### How W3/W6 tests should fake a successful result

Callers should reach the function through the module, as `from t2pw.service import
pathway` then `pathway.run_pathway(req)`, so that one patch target covers every caller. Or
they can inject the callable into the worker. Then:

```python
from t2pw.pipeline.release_status import RELEASE_READY, ReleaseStatus
from t2pw.service import pathway
from t2pw.service.pathway import PathwayResult, STATUS_PASS, STAGE_PWML_EXPORT

def fake_run_pathway(req):
    out = tmp_path / "out"; out.mkdir(exist_ok=True)
    pwml = out / "pathway.pwml"; pwml.write_text("<fake/>", encoding="utf-8")
    return PathwayResult(
        status=STATUS_PASS, stage=STAGE_PWML_EXPORT,
        release_status=ReleaseStatus(status=RELEASE_READY, pipeline_executed=True,
                                     strict_gates_passed=True),
        pwml_path=pwml, report_paths={"citation_report.json": out / "citation_report.json"},
        attempt_log=[{"attempt": 1, "status": STATUS_PASS}])

monkeypatch.setattr(pathway, "run_pathway", fake_run_pathway)
```

A failure fake is the stub itself, or `PathwayResult(status=STATUS_TIMEOUT,
failure_kind=KIND_TIMEOUT, ...)` for the W4 retry paths (`KIND_TIMEOUT`, `KIND_LLM`,
`KIND_NETWORK`).

## Dead ends and things not done

- **Considered: separate `pathway_name` / `organism` fields plus a `requested_scope()`
  method** (the `TopicSpec` pattern). Rejected. It redefines `RequestedScope`'s fields and
  copies the driver's `pinned` rule into the interface.
- **Considered: the stub raising `NotImplementedError`.** Rejected. W3/W4 could not run
  their failure and retry paths against it. A fixed error result exercises them.
- **Considered: `deadline` as a `time.monotonic()` value or a relative seconds budget.**
  Rejected for an absolute `time.time()` epoch. A monotonic value is meaningless in
  another process, and W3 cleans up "the job's own process tree", which suggests the run
  happens in a child process. See Q-W0-2.
- **Not done:** I did not mutation-check the tests (e.g. adding `import streamlit` to
  confirm the isolation test fails). The assertions are direct, but this is not proven.
- **Not done:** the stub does not validate `export_mode` or the inputs. Validation belongs
  to R5 or the web form.

## Open questions

**Q-W0-1. `out_dir` vs the app's fixed `PROJECT_ROOT/outputs`.** The app writes to a fixed
directory, and `reset_quarantine_state` clears it (R0 B1). Concurrent or queued jobs need
one directory per job.

| option | cost |
|---|---|
| A (recommended) | R5 honours `out_dir` by threading it through the moved functions. `None` keeps `PROJECT_ROOT/outputs` for the app. This touches R1/R4 signatures (a parameter with the old default), so it needs care under "R-tasks preserve behaviour" |
| B | R5 runs in the fixed directory, then copies the artifacts to `out_dir`. No signature changes. Only safe with W3's one-worker rule, and it breaks if two workers ever run |
| C | Drop `out_dir` from the interface. W3 then cannot separate jobs. Not viable for the queue |

**Q-W0-2. `deadline` semantics.** I chose an absolute epoch second, `None` = no cap.
Alternative: `timeout_s: float` relative, as the driver does (`_Budget(total, per_run)`).
That is simpler to test, but it is re-based on every retry and in every child process.
Changing it later is a field rename. Cheap now, a W3/W4 edit later.

**Q-W0-3. What W7 counts as a "strict PWML".** Is it
`release_status.status == "release_ready"` only? Or any PWML from a strict-mode run,
including `review_required`? Or should it also require `strict_acceptance_eligible`? This
is a product call. It does not change the interface, only how W7 reads it. If the PO
rejects carrying `release_status` at all, W7 falls back to the filename, which `RunOutcome`
documents as forbidden.

**Q-W0-4. Mirrored vs imported vocabulary.** I mirrored the vocabulary and test it. The
alternative after R6 is to move the constants into `t2pw.service.pathway` and have the
driver import them. That is one source and no mirror test, but it is an edit to
`batch/driver.py`, so it belongs to R6, not W0.
