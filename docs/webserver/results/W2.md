## The query and why the join is right

```sql
SELECT id, name, taxonomy_id, common_name, classification FROM species ORDER BY id
SELECT DISTINCT species_id FROM pathways WHERE species_id IS NOT NULL   -- has_pathways flag only
```

- The species list comes from the `species` table alone, so no join can mis-attribute anything.
  `SHOW COLUMNS` confirmed `species(id, name, taxonomy_id, common_name, classification, ...)`;
  `taxonomy_id` is a **varchar** (e.g. `'0989088'`), kept as a string.
- `pathways.species_id -> species.id` is used only for the `has_pathways` flag. Checked against known
  species before trusting it: Homo sapiens (id 1, taxon 9606) has 171,388 pathway rows, Mus musculus
  (12) 131,931, Rattus norvegicus (17) 98,083, Bos taurus (5) 56,289, Escherichia coli (3, taxon 562)
  12,369. 1,127 distinct species have at least one pathway row.
- PW accession lookups (`spv.pw_id`, not `pathways.id`) are not involved: no accession is read or emitted.
- Only SELECTs are issued; the fake-cursor test asserts every statement starts with SELECT.

## Matching: how PathBank names map to the pipeline string

`scope` = PathBank `name`, stripped, verbatim. No remapping, because the pipeline already normalises:
`_organism_aliases` (lexicon first, else the normalised full name plus the abbreviated genus
`e coli`) and `_taxon` (drops strain suffixes, compares genus+species). Measured with
`rag.eligibility` on this export (uncommitted probes `C:/t/wsW2tmp/stats.py`, `probe3.py`):

| class | count | pipeline behaviour |
|---|---|---|
| exact lexicon entry (e.g. `Homo sapiens`, `Escherichia coli`, `Mus musculus`) | 44 | full lexicon aliases (`human`, `patients`, `mouse`...) |
| binomial (genus + species) | 3748 | species-level match; abbreviated genus alias |
| non-binomial (no species token) | 270 (83 with pathways) | equality-only comparison |
| parenthesised / `str.` / `strain` names | 333 | e.g. `Escherichia coli (strain K12)` matches an observed `Escherichia coli` (`compare_organism` -> `match`, asserted in the test) |
| names starting with `[genus]` brackets (`[Candida] auris`) | 34 | `_normalize` strips the brackets, so they alias as `candida auris` |

## Edge cases (not changed; for the product owner)

1. **Strains are separate species rows** (`Escherichia coli`, `... (strain K12)`, `... O157:H7`, about 60
   E. coli rows). The drop-down offers all of them (D-W04). A strain pick still matches papers that say
   only "E. coli" (strain suffix dropped) but will not prefer strain-specific papers.
2. **`sp.` / unclassified names** (`Bacteroides sp. 1_1_14`) are non-binomial for `_taxon`, so they match
   only by equality of the whole string; papers almost never contain it. Eligibility will be weak.
3. **Genus-only or higher rank** (`Bacteria`, `Acer`, `Homo`, `Circovirus`): same equality-only rule.
4. **Junk / test rows exist in the PathBank `species` table**, e.g. `Test`, `kjhkjh`, `peter`, `rac1`,
   `Andrographolide`, `homotera`, `Homosapiens`, `Homo sapiens 1`, typo `Saccharomyces cerevisae`
   (taxon 15). Exported as-is per D-W04.
5. **Duplicate name:** `Serratia marcescens` is in the table twice (ids 284 and 1932). Labels become
   `Serratia marcescens [PathBank id 284]` / `[... 1932]`; both keep `scope` `Serratia marcescens`.
   One name had stray whitespace (stripped). No NULL/blank names exist; the script would skip them.
6. `classification` in PathBank is unreliable (e.g. `Saccharomyces kudriavzevii` is "Prokaryote"). It is
   exported but should not drive any logic.

## Dead ends

- `SET SESSION TRANSACTION READ ONLY` as a belt-and-braces read-only guard: the server rejects it
  (`1193 Unknown system variable 'TRANSACTION'`, old MySQL/MariaDB). Dropped; read-only is by use
  (SELECT only), same as the `pathbank_gold.connect` docstring ("read-only-by-use").
- pymysql treats `args=()` as a format request, so a `%` in a probe `LIKE` needed `args=None`. Probe only.
- A first secret scan flagged `RAG_ENABLED` / `PATHBANK_DB_PORT` values: false positives (`true`, `3306`).
  Re-scanned only for HOST/USER/PASS/KEY/TOKEN/SECRET/EMAIL values of length >= 6: 0 hits.
- The probing queries (three short scripts, all SELECT) were run directly rather than through the
  wrapper; the real export and every test went through `bounded_run.py`.

## Open questions (product owner)

1. **Filter the junk?** D-W04 says all PathBank species, so all 4018 are in. A user can pick `Test` or
   `peter`. Options: (a) keep all (current; no data loss, ugly drop-down); (b) hide `has_pathways=false`
   (1127 shown; the flag is already in the JSON, so this is a UI-side filter with no re-export); (c) a curated
   allow-list (cleanest, needs a human pass over about 4000 names). Cost of (b): species PathBank knows but
   has no pathway for become unselectable.
2. **Strain granularity.** Keep the ~330 strain rows (current), or collapse to species with a strain
   note? Collapsing needs a taxonomy decision and changes what the user can request.
3. **A 4018-item drop-down** needs a searchable control (W5/W6 concern), not a plain select.
4. **Refresh cadence.** The JSON is a snapshot of the DB at export time; re-run the script when PathBank
   adds species. No scheduler was built.
