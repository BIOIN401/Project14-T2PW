## Design decisions, in brief

1. **Two CSS files, not three.** `tokens.css` holds only tokens, so the theme test reads
   one file. `site.css` holds base styles and components. A third file would only add a
   request.
2. **Themes.** Light is the default. Dark follows `prefers-color-scheme`. The manual
   override hook is `data-theme="light"` or `data-theme="dark"`, on `<html>` (through the
   `theme` variable) or on any element, which themes only that subtree. That subtree
   mechanism is how the styleguide shows both themes on one page. CSS cannot share one
   rule between a media query and a plain selector, so the dark values appear twice. The
   test asserts the two dark blocks are identical.
3. **`light-dark()` rejected.** It would remove the duplication, but it has only been
   broadly available since 2024. Reviewers may use older browsers, and the brief asks for
   a test that both themes define the same token set, which needs explicit blocks.
4. **Colour direction.** Placeholder until the PO decides (see Open questions). The
   primary is a deep teal-blue (`#0b5f7f` light, `#5bb8d6` dark) on cool neutral greys.
   Status colours: queued = neutral, running = info blue, done = green, failed = red,
   review required = amber. Every badge carries a text label, so colour is never the only
   signal (WCAG 1.4.1). Queued also has a hollow dot, and running has a pulsing dot.
5. **Contrast is tested, not asserted.** The test computes the WCAG ratio for 30 text
   pairs (≥ 4.5:1) and 5 non-text pairs (border-strong and focus ring, ≥ 3:1) in both
   themes. All colour tokens are `#rrggbb` so the test can parse them.
6. **Accessibility basics.**
   - Semantic landmarks: header, nav, main and footer.
   - A skip link.
   - Every input has a `<label for>`. Hints and errors are tied to their input through
     `aria-describedby`, and an error sets `aria-invalid`. The test checks every `for=`
     points at an existing id.
   - Required fields carry both the `required` attribute and a visible "required" word.
   - A visible `:focus-visible` ring, using its own `--color-focus` token.
   - 44 px minimum height for buttons and inputs.
   - The step indicator marks the current step with `aria-current="step"`, and each state
     has visually hidden text.
   - Error alerts use `role="alert"`; info and warning alerts do not.
   - The table sits in a focusable `role="region"` that scrolls sideways.
   - `prefers-reduced-motion` stops the running-badge pulse and transitions.
7. **No JavaScript, fonts or CDN.** A system font stack, no `<script>`, no `url()` and
   no `@import`. Glyphs (✓, !, ↓) are CSS `content`. All of this is tested.
8. **Neutral copy.** The styleguide uses placeholder text only. The step-indicator demo
   uses the raw `STAGE_*` keys from `src/t2pw/service/pathway.py` as labels. The real stage
   names are W6 copy.

## Findings, dead ends, things not done

1. **The contrast test caught a real defect on its first run.** The first dark
   `--color-danger-hover` (`#dd4c41`) is lighter than the base colour, and white text on
   it measured 4.05:1. I darkened it to `#a82c23` in both dark blocks. Evidence:
   `01-focused.log`.
2. **Headless Chrome follows the OS theme.** The first "light" screenshot rendered with
   dark page chrome, because this machine is in dark mode. Fix: the light and dark shots
   use the forced `data-theme` variants. This incidentally exercises the override hook in
   a real browser.
3. **A wrong theory, ruled out: "the page overflows at 360 px".** The first mobile shot
   (`--window-size=360,…`) showed clipped text, swatches and buttons. I suspected the
   styleguide's `auto` grid track and changed it to `minmax(0, 1fr)`. The shot did not
   change. The real cause is that headless Chrome enforces a minimum window width of about
   500 px: it laid the page out at about 500 px and cropped the image to 360. Framing the
   page in a 360 px iframe gives a true 360 px viewport, and that shot wraps correctly.
   The table scrolls inside its own wrapper as designed. I kept the `minmax(0, 1fr)`
   change: it is correct and harmless.
4. **Not done:**
   - No dark-theme mobile shot.
   - No automated keyboard-navigation test. Only the static structure is tested: labels,
     ids, focus CSS, the skip link.
   - No screen-reader pass.
   - The radio group uses default browser radios, not a segmented control. A segmented
     look is a W6 call, if wanted.
5. **Added beyond the brief's component list:** `radio_group` (a fieldset of radios).

## Notes for W6

The same text is at the top of `src/t2pw/web/templates/macros/components.html`:

- `href` values, `attrs` keys, `variant` and `heading_level` must be built by the server,
  never taken from user data. Autoescaping stops markup injection, but not a
  `javascript:` URL in an href, an event-handler key in `attrs`, or a forged class or tag
  name.
- Autoescape must stay on for `.html` templates (the `Jinja2Templates` default). The
  macros rely on it to escape labels, values and unknown statuses.
- `templates/` and `static/` are not Python files. Add them as package data (pyproject or
  MANIFEST) before the server is installed from a wheel. W5 does not do this.
