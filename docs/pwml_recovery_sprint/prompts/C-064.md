## 1. The defect, measured at the base SHA

`src/t2pw/rag/loop_policy.py:138-143` — **one property, two unrelated bounds:**

```python
@property
def out_of_budget(self) -> bool:
    """No further round is affordable. The round bound and the time bound each
    stop the loop independently, which is what makes the loop bounded."""
    return (self.rounds_completed >= self.max_rounds
            or self.deadline - self.now <= self.next_round_reserve_seconds)
```

`loop_policy.py:170` maps that straight onto the D-005 operational-failure reason:

```python
BUDGET_EXHAUSTED: state.out_of_budget and not exhausted,
```

* **The time bound** — `deadline - now <= next_round_reserve_seconds` — is genuine resource exhaustion. The
  run wanted more and the clock refused. `budget_exhausted` is the honest label.
* **The round bound** — `rounds_completed >= max_rounds` — is **a configured ceiling being honoured.** The
  loop did exactly what it was told. Reporting that as an operational failure reports **a policy success as
  a malfunction.**

**Why this is HIGH and not a labelling nicety:** `src/t2pw/rag/controller.py:237` defaults
**`max_rounds: int = 1`**. On the default configuration, **every RAG loop that completes round 1 and would
have continued reports `budget_exhausted`.** Not an edge case — the default path. The exemption
(`and not exhausted`) suppresses it only when the ladder completed *and* `new_admissible_claims <= 0`; the
round that **did** produce integrable claims — the interesting case, the one T-103 exists to exercise — is
precisely the one mislabelled.

**Live in production since C-055 merged.** `src/t2pw/app/streamlit_app.py:1426` calls `run_rag_loop`.

## 3. Required behaviour

**Split the round bound from the time bound**, and give the configured-ceiling stop **its own termination
reason, outside the D-005 operational-failure set.**

Hard constraints:

1. **`budget_exhausted` must keep its operational-failure meaning.** After your change it must fire when, and
   only when, a **genuine** time/resource bound stopped the loop (subject to the existing `not exhausted`
   carve-out).
2. **Do NOT widen the `and not exhausted` exemption.** F-070 names this explicitly: it would suppress the
   reason on runs where the time bound genuinely fired, trading a false positive for a false negative in the
   denominator that matters more.
3. **Boundedness is a load-bearing invariant and must survive.** `decide` documents it at `:190-193`: *"a
   state in which no condition holds continues, and `out_of_budget` always yields one, so the loop stays
   bounded."* After the split, **reaching either bound must still always yield a stop reason.** Prove this —
   an unbounded RAG loop is a far worse defect than a mislabelled one.
4. **`_conditions` must keep a key for every member of `TERMINATION_PRECEDENCE`.** The docstring at `:158-162`
   explains why: `decide` indexes the mapping by precedence member, so a missing key is a `KeyError`, not a
   silent omission. Your new reason needs both.
5. **`TERMINATION_REASONS` (`:55`) is derived from the precedence tuple.** Check every consumer of that
   frozenset before assuming a new member is free.
