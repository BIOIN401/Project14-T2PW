## 2. The defect

`src/t2pw/pwml/compound_resolution.py:592-599`, in `_resolve_compound_rows`:

```python
if db_resolver is None:
    try:
        from t2pw.mapping.map_ids import PathBankDbResolver
        db_resolver = PathBankDbResolver.from_env()      # <- ambient DB substituted
    except Exception as exc:
        db_reason = f"db_resolver_unavailable:{exc}"
        db_resolver = None
```

`None` is overloaded. It currently means **"I did not specify one — go find one"**. It is also the
only value a caller has available to mean **"resolve no compounds against a database."** The two
readings are conflated and the second is unreachable: a caller that deliberately disables DB
resolution silently gets the ambient live database, and nothing in the report says so.

## 3. The intended semantics — derived, not guessed

**This card does not need a product-owner ruling.** The production intent is documented in the
source and tied to the contract:

`src/t2pw/pwml/prefreeze_resolution.py:353-359`:

> *"`db_resolver=None` and an unset `name_index` reproduce exactly what `build_pwml_ir` passes
> today, so **this call — not the exporter — is the one that opens the PathBank connection**
> (`PRODUCT_CONTRACT` §8), and the resolution outcome is the same one the exporter would have
> reached."*

Reinforced at `prefreeze_resolution.py:1709-1719` and `pwml/ir.py:33-48`, both citing **D-015** and
**D-032 clause 6**.

So:

* **`None` = "unspecified → open the ambient connection" is INTENDED, load-bearing, and
  contract-bound.** The pre-freeze call must open the connection precisely so the *exporter* never
  does. **Do not change it.** Making `None` mean "no DB" would push the lookup into the exporter and
  violate `PRODUCT_CONTRACT` § 8 outright.
* **What is missing is a third state:** an explicit *"no resolver"* a caller can pass.

**The answer to the charter's question is therefore: `None` means "use a separately explicit ambient
resolver", and the fix is to ADD the missing "no resolver" value — not to redefine `None`.**

## 4. Required direction — binding

* Add an **explicit sentinel** meaning *"resolve nothing against a database"* — a module-level
  singleton (e.g. `NO_DB_RESOLVER`), not a bare `False`, not a magic string, not a second boolean
  parameter that can contradict the first.
* Thread it from the public entry points (`run_prefreeze_resolution`, and any other caller-facing
  signature that accepts `db_resolver`) down to `_resolve_compound_rows`.
* **Preserve `None` semantics exactly.** Every existing production caller that passes `None`, or
  omits the argument, must keep getting the ambient resolver. This is the preservation obligation
  and it is the one most likely to be broken by an over-eager fix.
* **Preserve callers that intentionally pass a real resolver.** Unchanged.
* When the sentinel is passed, the report must record it **distinguishably** — `available: False`
  with a reason that says *the caller disabled it*, not one that implies a lookup failed. Do not
  reuse a reason that means something else. Note the existing vocabulary already distinguishes
  `db_not_configured` from `harvest_db_down`; add to it in the same spirit.
* **An ambient live database must never silently change the behaviour of an explicitly offline
  caller.** That is the whole point of the card.
