## 3. What to build

### 3.1 Re-pin the census — `==`, never `>=`

Move all four pins to their measured values: `legs == 72`, `checked == 72`, `withheld == 97`,
`with_matched_forbidden == 26`. Raise the line-375 floor to `>= 72` so it keeps catching a
**shrink** against current truth.

**Do NOT relax any of them to `>=`.** I proposed exactly that in F-151 and REV-104 talked me out of
it, with a reason I had not considered and now accept:

> *"`test_10` and `test_13` pin **derived** quantities (`legs`, `checked`) **against that census**;
> relaxing them to `>=` means the suite stops noticing that ten new legs entered the population
> unremarked."*

Line 325's `>=` guards a **floor** — did the corpus shrink. Lines 347/461 assert that a loop
**visited every leg it should have**, and the census is how they know how many that is. A `>=`
there would let a leg join the corpus and go unvisited, which is the opposite of the guard's
purpose and is a quiet vacuity of exactly the F-144 shape.

**The cost is that the pin must be moved deliberately every time a run is committed. That is the
correct cost** — moving it is the moment someone confirms the new legs were meant to be there.

Beside each moved pin, record **why it grew**, naming `runs_verify/2026-08-28_1816`, commit
`e77ad3d`, and that run's exact contribution (10 legs / 5 terms / 3 legs). A number moved without
its reason is the defect recurring one wave later.

**This is merge rule 4's escape hatch used correctly:** a pinned baseline moved deliberately, with
an exact documented delta attributable to exactly ten legs from one named run.

### 3.2 Make the harness runnable and D-084-compliant

* **Saved-bytes restore.** Read the target with `read_bytes()`, keep the original `bytes` in
  memory, write the mutant with `write_bytes()`, and restore by writing the **saved bytes back**.
  **Remove the `git checkout --` restore entirely** — it is what has been masking the line-ending
  damage. Assert `sha256(after) == sha256(before)` per mutation, not merely
  `git status --porcelain == ""`, because a clean status is exactly what `git checkout --` produced
  while the harness was corrupting the file.
* **The baseline precondition.** It must still refuse to certify mutations against a red suite —
  that assertion is correct and load-bearing, and deleting it would make every mutation result
  meaningless. Once § 3.1 lands, the baseline is green and the precondition is satisfiable. **Do
  not weaken it to make the harness run; fix the census first and let it pass honestly.** Keep the
  message, and make the failure state the actionable thing ("the census pin is stale — see C-106")
  rather than a bare assert.
* **Then run it, with all eight mutations** (`M1`–`M7` plus C-104's `R5`). Commit the log. Every
  mutation must go RED; any GREEN is a finding to report, not to fix.

### 3.3 Scope the count parse to pytest's summary line

Parse counts from pytest's own summary line, not from the whole stream. The summary is the last
line matching pytest's `N passed`-style terminal report; anchor on it rather than scanning
free text. **Do not touch the abort predicate at line 81** — that is C-104's, it was reviewed and
merged, and widening or narrowing it here is out of boundary.

### 3.4 New focused coverage — `tests/test_c106_mutation_harness_executable.py`

**G9 label: NEW ACCEPTANCE TEST, new capability.** No fabricated base failure. Say so explicitly.

It must prove the harness is **executable and non-vacuous** — the two things F-151 says nobody
could claim:

1. **Every mutation still applies.** Import `MUTATIONS` from the harness and assert each `old`
   string occurs **exactly once** in its target file. This is the non-vacuity guard: a mutation
   whose substitution silently matched zero times produces a green suite that reads as a pass.
   This test is what catches a future refactor renaming a mutated line out from under the harness.
2. **The restore is byte-exact.** Apply and restore one mutation through the harness's own restore
   path and assert the file's `sha256` **and its CRLF count** are unchanged. This is D-084 pinned
   as a test rather than as a review habit.
3. **The baseline precondition is satisfiable** — the c102 suite is green — so the harness's own
   abort cannot be the reason a future run reports nothing.

Item 2 must fail if someone reintroduces `write_text(newline="")`. **Mutate your own guard and show
it goes red**, per R7 / F-144.
