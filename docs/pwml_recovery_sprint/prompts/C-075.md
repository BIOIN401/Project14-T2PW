## 3. The product owner's ruling — this governs the design

> A real identifier may survive only when the entity's identity **and biological kind** are
> supported by paper evidence, a proven alias, or another permitted provenance route.
> **Do not require the literal database accession to appear in the paper.** Unsupported or
> hallucinated entities must not acquire real identifiers. Legitimate aliases must retain valid
> mappings.

Three consequences you must honour:

1. **Never look for the accession string in the paper.** Support is about the entity being named or
   provably aliased, never about `CHEBI:15380` appearing in the text. The existing
   `identity_support` already works on names — keep it that way.
2. **Kind must be supported too, not just identity.** A row whose name is present but whose
   biological kind contradicts the evidence is not supported merely because the string occurs.
   The cross-kind accession rule already covers the accession-sharing case; consider what, if
   anything, is needed for a row whose kind is unsupported on its own. **If you conclude nothing
   further is needed, say so with evidence rather than adding a speculative gate.**
3. **A proven alias is a permitted route.** `candidate_names` already includes `aliases`,
   `short_name` and enrichment `synonyms`. Preserve that. All six measured alias cases
   (`2,3-dihydroxybenzoic acid`↔`…benzoate`, `L-serine`↔`Serine`,
   `Adenosine triphosphate`↔`ATP`, `Adenosine monophosphate`↔`AMP`,
   `ferric-enterobactin`↔`ferric enterobactin`, `Fe3`↔`Fe3+`) must keep their identifiers.
