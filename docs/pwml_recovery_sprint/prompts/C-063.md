## 4. Required behaviour

### 4a. Mutex — fold acquisition into `bounded_run.py`

F-072 names this the stronger of two candidates precisely because it removes the primitive from agent hands.
Implement it so that **the shell cannot get past a failed acquire**:

1. A new flag (name it as you see fit; `--heavy-lock <holder>` is a reasonable default) makes the wrapper
   acquire `C:/t/heavylock` **atomically** before spawning the child. Keep `mkdir`-style `O_EXCL` semantics —
   the primitive is correct, only its consumption was broken.
2. **A failed acquire must not run the child.** Exit non-zero with a distinct, documented status, and print
   the current holder file contents so the caller can see who holds it without a second command.
3. On acquire, the wrapper writes the holder file itself, containing at minimum holder/role, label, PID and
   the command. The agent must not have to remember to do it.
4. **Release only if the holder file names this job.** If it names someone else — or has vanished — the
   wrapper must **refuse to remove it**, say so loudly, and report the condition. This is the rule that
   converts the F-072 failure from silent to visible.
5. Release must happen on **every** exit path the wrapper controls, including timeout kill and child crash.
6. **The flag is opt-in.** Every existing call site that does not pass it must behave exactly as today.

### 4b. G11 report lifecycle — remove the failure mode, do not paper over it

F-071 evaluates three candidates and names only one as removing the failure mode rather than hiding it:
**`next` writes to a staging path that `bounded_run.py` promotes on completion, so an unfinished job leaves
nothing in the reports tree at all.**

Implement that one. Constraints that make it non-trivial and that you must satisfy:

* **The uniqueness guarantee at `g11_evidence.py:120-129` must survive.** It is structural, not
  probabilistic: task directory + `max(existing)+1` + `O_CREAT|O_EXCL`, and **sequences are never reused, so
  a re-run cannot overwrite the report of the attempt it replaces.** If staging moves the reservation out of
  the reports tree, say exactly how two concurrent allocations still cannot collide, and how a sequence still
  cannot be reused. **If your design cannot preserve this, stop and report — do not weaken it.**
* **The `allocate()` anti-abuse purpose must survive.** The placeholder exists so an agent cannot hand-write
  a `--json` path and abandon the audit trail. A staging design that lets any path through defeats it.
* **Promotion must be all-or-nothing.** A partially written report in the reports tree is worse than none;
  `emit_json_report:1032-1034` already serialises before opening for exactly this reason.
* The `check_report` `report_never_written` rule (`:186-187`) still has to fail a placeholder that does reach
  the reports tree by any route. Do not delete that rule.
