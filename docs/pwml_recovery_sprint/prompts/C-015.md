OBJECTIVE
  PRODUCT_CONTRACT section 3 requires the final pathway to distinguish at least:
  explicitly stated in the supplied paper | added from RAG-supported external
  literature | grounded through a biological database | added through
  deterministic inference | added or changed by audit/repair | unresolved or
  excluded.

  This exists so that false content can be attributed EMPIRICALLY to Stage 1,
  RAG, inference, audit, mapping, gap resolution or another stage. Today the
  baseline reports 10 false real identifiers and 7 unsupported reactions with no
  way to say which stage introduced them -- that is exactly the question R-003
  and R-004 are trying to answer by hand.

  After this patch: a single module defines what a lineage record is, every
  producing stage has one obvious way to write one, and a consumer can ask "which
  stage introduced this entity, and on what evidence?" and get a typed answer.

REQUIRED OF THE SCHEMA
  Per PRODUCT_CONTRACT section 3, every externally added entity and process must
  identify:
    - the stage that introduced it
    - why
    - its supporting source or database record
    - whether it was paper-explicit
    - its evidence/support level
    - any uncertainty or review requirement

  The schema MAY differ from that wording; the INFORMATION must be traceable.

IMPLEMENT
  1. A typed lineage record. Enumerate the stages as a closed vocabulary -- a
     free-string `stage` field will be filled with seven spellings by seven
     branches and the attribution question stays unanswerable.
  2. A closed vocabulary for origin/support level covering the six
     PRODUCT_CONTRACT categories above.
  3. Append semantics. Lineage is a HISTORY: audit/repair adds to it, it does not
     overwrite what an earlier stage recorded. A design that lets a later stage
     erase an earlier attribution defeats the purpose.
  4. A validation helper that rejects a malformed record loudly at write time.
     A silently-dropped lineage entry is worse than none, because it reads as
     "this content was original".
  5. Serialization that is STABLE and ORDER-INDEPENDENT where order is not
     meaningful. C-013's graph projection must be able to exclude lineage
     wholesale, and C-020's comparator must treat two equivalent lineages as
     equal. Coordinate with neither -- just do not make it order-sensitive.
  6. Nothing in this module may import a stage module. It is a leaf.

MUST NOT CHANGE
  - Anything. This branch adds one new file and one new test file. If you find
    yourself editing an existing source file, STOP -- that file belongs to one of
    the seven downstream branches.

TESTS YOU MUST ADD

     round-trips through serialization unchanged.
  b) A malformed record is rejected, with a message naming the offending field.
  c) Append preserves earlier entries; no writer can erase another's attribution.
  d) Two lineages differing only in the order of independent entries compare
     equal; two differing in content do not.
  e) An unknown stage or origin value is rejected, not silently coerced.
