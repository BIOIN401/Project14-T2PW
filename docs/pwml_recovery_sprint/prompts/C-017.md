  D-006: semantic checks must affect the actual runtime release_status. Wiring

  release_ready having never been semantically evaluated at all -- and the

  around a GoldCase, and production has no gold case.

  After this patch: a module exists that evaluates the semantic quality of a
  produced pathway WITHOUT a gold case, returns a report that distinguishes all
  five D-006 states, and is importable by the runtime without dragging in the
  benchmark harness.

REQUIRED SEMANTICS -- D-006 and PRODUCT_CONTRACT section 11
  The result must distinguish, WITHOUT collapsing any into another:
    - pipeline execution succeeded
    - strict technical gates passed
    - semantic evaluation passed
    - semantic evaluation failed
    - semantic evaluation WAS NOT PERFORMED
  not_evaluated is NEVER false. A check that could not run is excluded from
  "confirmed" and is NOT counted as a pass. This is already how semantic.py
  behaves (:293) -- preserve that property, do not re-derive it.

IMPLEMENT
  1. A production entry point taking the produced payload and the requested
     pathway/organism context -- NOT a GoldCase.
  2. Reuse the existing CheckResult / SemanticReport vocabulary rather than
     inventing a parallel one. C-056a has to merge your verdict into
     release_status; two vocabularies make that merge lossy.
  3. Implement only checks that are answerable WITHOUT gold data. A check that
     needs a gold answer must report not_evaluated with a reason, not fail.
  4. Every check states explicitly whether it is applicable to this payload.
     "Not applicable" and "failed" are different answers.
  5. No import of bench/goldset.py, acceptance.py, or any benchmark runner. If
     the runtime has to import the benchmark harness to classify a run, the
     dependency is backwards.
  6. No network, no database, no LLM call. This runs inside the pipeline's
     deadline.
